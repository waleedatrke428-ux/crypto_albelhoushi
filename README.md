# كريبتو البلحوسي

مستودع لتطبيقين Android منفصلين مبنيين بـFlutter:

- `apps/user_app`: تسجيل/دخول Supabase، حالة التجربة والاشتراك، الإشارات المسموح بها، سجل التسليمات، بيانات السوق، الإشعارات، طلبات الدفع ورسائل الدعم.
- `apps/admin_app`: دخول مدير محمي بالدور، لوحة إحصاءات من قاعدة البيانات، إدارة المستخدمين والاشتراكات، نشر إشارة مجانية/مدفوعة، متابعة نتائج الإشارات، مراجعة الدفع، الإعدادات ورسائل الدعم.

التطبيقان لا ينفذان أوامر تداول. نشر الإشارات للمستخدمين يعتمد على سجل `signals`، وتوزيع التسليمات والإشعارات يتم بواسطة trigger في ترحيل Supabase. لا يوجد مولّد ذكاء اصطناعي أو تغذية شموع/أخبار/Push ضمن قاعدة البيانات التي زودت بها؛ يجب ربط هذه الخدمات منفصلًا قبل تفعيلها.

## إعداد Supabase

1. احتفظ بنسخة احتياطية من قاعدة البيانات.
2. افتح Supabase Studio ثم **SQL Editor** وشغّل [ترحيل أمان التطبيق والوصول](./supabase/migrations/202610190001_app_access_and_signal_fields.sql).
3. يتطلب الترحيل أن يطابق `public.users.id` قيمة `auth.users.id`. ينشئ trigger ملف المستخدم وفترة تجربة 6 أيام تلقائيًا عند التسجيل. إذا كانت لديك حسابات قديمة بمعرّفات مختلفة، أوقف الترحيل وراجع ربطها أولًا؛ الترحيل يرفض هذا التعارض بدل ربط الحسابات خطأ.
4. عيّن دور حساب المدير يدويًا من Supabase Studio إلى `admin` في `public.users.role` بعد التأكد من أن صف المستخدم يعود لحساب Auth الصحيح.
5. لا يضع التطبيق مفاتيح الخادم فيه. استخدم رابط مشروع Supabase ومفتاح `anon/public` فقط في بناء التطبيق. لا تضع `service_role` أو مفاتيح منصات التداول في تطبيق الهاتف أو المستودع.

يضيف الترحيل حقول `exchange`, `timeframe`, `rationale`, `strength`, `is_free`, `status`, `result`, و`closed_at` إلى `signals`، ويضيف ربط المستخدم والصفقة إلى `notifications`، ويفعّل RLS على الجداول العشرة. كما يضيف دوال آمنة لتوزيع الإشارات وتفعيل الاشتراك أو اعتماد الدفع من المدير.

## إعداد بناء APK على GitHub

في إعدادات المستودع، أضف GitHub Actions repository secrets:

- `SUPABASE_URL`: عنوان مشروع Supabase.
- `SUPABASE_ANON_KEY`: مفتاح `anon/public` الخاص بالمشروع.

بعد رفع التغييرات:

1. افتح تبويب **Actions**.
2. شغّل **Build Android APKs** يدويًا أو ادفع تغييرًا إلى `main` أو `master`.
3. نزّل `crypto-user-apk` و`crypto-admin-apk` من Artifacts لتشغيل الـ workflow.

ينشئ GitHub ملفات Android ويبني APK لكل تطبيق، ولا يلزم تثبيت Flutter أو Java محليًا لهذا المسار. أسرار البناء تُمرر إلى `dart-define`؛ تذكّر أن مفاتيح `anon/public` ليست سرًا أمنيًا داخل APK. يعتمد أمان البيانات على سياسات RLS ودوال الخادم.

## حدود الميزات الحالية

- الإشارات المتاحة يقيّدها RLS بحسب الاشتراك/التجربة، أو تُعرض للجميع عندما تكون `is_free = true`.
- تأكيد الدفع ينشئ الاشتراك ذريًا عبر دالة قاعدة البيانات؛ لا يُفترض أن يعلن التطبيق الدفع مكتملًا دون اعتماد المدير.
- سجل الفوز/الخسارة يعتمد على تحديث المدير لنتيجة الإشارة. لا يحتوي المخطط على مراقب أسعار يكتشف تلقائيًا وصول الأهداف أو وقف الخسارة.
- جدول `market_data` يعرض آخر صفوف يرسلها مزود بياناتك، وليس تغذية أسعار مستقلة من التطبيق.
- المخطط لا يحتوي شموعًا تاريخية، رابط شارت، أخبارًا، أو رموز أجهزة للإشعارات الدفعية؛ الواجهات تعرض غياب هذه المصادر بوضوح بدل بيانات مختلقة.
- التقارير العددية تُحسب من الصفوف التي تسمح بها RLS. للمشاريع الكبيرة، استبدل تحميل كل السجلات بتقارير RPC مجمّعة ومحدودة من الخادم.
- التداول في العقود الآجلة عالي المخاطر، والإشارات ليست ضمانًا للربح.
- قد يتطلب تثبيت APK يدويًا السماح بالتثبيت من مصدر خارجي. لم يُضبط توقيع Google Play.
